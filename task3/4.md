## Описание релиза

### Состояние на начало месяца

Февраль 2027, 01.02–28.02, четыре недели. Мажорный выпуск истории изменений планируем на 12.02; минорные изменения выпускаем по готовности. Правила учёта сохраняем из [раздела «Метрики»](task3.md#метрики), обязательства сервиса — из [ПР1](../task1.md), процедуры работы — из [ПР2](../task2.md).

На начало февраля QS обслуживает 1 820 проектов и 9 100 шардов. Январский отчёт показывает Read availability 99,95%, Read p95 194 мс, failed deployments 5% (1 из 20), ручные L2 196 ч и L3 110 ч, Write availability 99,70%. В очереди 40 проблем. В наиболее нагруженной зоне d средняя/пиковая нагрузка Read — 210 000/420 000 RPS, Write — 2 300/4 800 RPS; остальные зоны не выше. Все RPS и мощности далее относятся к одной зоне, количество проектов и шардов — ко всему QS.

Из января переходит R3-AUDIT: нужно закрепить ответственного за доказательства, согласованные область и получателя выгрузки, сделать воспроизводимый пакет и проверить запрет выдачи чужого проекта. Технически получить данные уже можно, но без согласия владельца проекта этого недостаточно для допуска пилота. На завершение отведено 40 ч: лид 4, senior 8, middle 1 — 8, junior 4, поддержка 6, SRE 8, продукт 2. Стоимость внутри фонда — 70 750 ₽. Внедрение планируем на 12.02, приёмку — до 15.02. Шесть часов поддержки здесь — обучение и приёмка, а не повторный учёт ручной L2.

Регулярное обязательство — 2 ч L2 и 2 ч L3 middle 1 в месяц на актуальность согласий владельцев, получателя и выборку полноты аудитного пакета. Это 5 000 ₽ внутри фонда и ручных метрик. Январская разовая работа с паспортом миграции уже закончена, её часы дальше не переносим. Других новых регулярных ручных обходов нет; обычное сопровождение остаётся в эксплуатации.

Наследуем 7 реплик QS на зону и ресурс YDB: проверенная устойчивая мощность 560 000 Read/7 200 Write RPS, при одной выведенной реплике — 480 000/6 200. Отдельно пройден пик 600 000/5 000 продолжительностью до часа, в том числе на шести репликах. Этот кратковременный режим не заменяет устойчивую мощность. Накопленная добавка инфраструктуры — 260 000 ₽/мес. за все зоны.

### Цель и первоначальный состав работ

При вопросе «куда делась квота» поддержка собирает по кускам переносы автоматики, ручные изменения и создание дерева по шаблону. Мы даём владельцу проекта API истории и диагностику по traceId, чтобы он мог увидеть применённое изменение и причину отказа без выгрузки логов через инженера. Цель февраля — уменьшить ручную работу при росте числа проектов, сохранив клиентские обязательства.

| Метрика | Цель февраля |
| --- | ---: |
| Доступность Read API | ≥ 99,90% |
| p95 Read API | ≤ 200 мс |
| Доля неудачных выкаток, включая минорные | ≤ 8% |
| Ручные часы L2 | ≤ 160 ч |
| Ручные часы L3 | ≤ 95 ч |
| Доступность Write API | ≥ 99,00% |

QS показывает состояние квот и принятый юзадж. Потребление считает coremon, лимиты применяют сервисы-потребители, счета выставляет биллинг. До R9 работаем только с квотами метрик. В этом релизе меняем API и процедуры поддержки; UI в работах и бюджете отсутствует. Внутренние бюджеты часов и доля неудачных выпусков не являются отдельными основаниями для клиентских кредитов. Клиентский SLA ПР1 сохраняет Read ≥ 99,9%, p95 Read ≤ 200 мс, Write ≥ 99% и восстановление P1 ≤ 70 минут.

На старте планируем три крупных элемента. Здесь ещё нет будущих внеплановых обязательств; часы — разработка, тестирование, внедрение и приёмка, отдельно от ручной L2/L3.

Предупреждение использует committed-версию и своё окно потребления. Поэтому для R5 не нужно заново менять формат истории.

Базовая история доступна за последние 30 дней: до 100 событий на страницу, до 7 дней в одном запросе, поиск только внутри проекта. Возвращаем history_available_from: события до включения истории не восстанавливаем по догадке, прежние журналы выдаём по каталогу ПР2. Его полезность — меньше повторных запросов за длинный период; цена — отдельные проверки прав, полноты и ограничения нагрузки. Массовая выгрузка dry-run на 48 ч остаётся отдельной необязательной задачей без даты, в февральский план не входит.

Ожидаемый риск — тяжёлый поиск истории вытеснит чтение текущих квот из YDB. Готовим индекс по проекту и версии, ограниченные страницы и отдельный пул истории: до 200 RPS на зону и 5 RPS на проект. Прогоняем максимальный поток истории одновременно с основными Read/Write. При превышении порога останавливаем подключение новых потребителей истории; принятые события и квоты не удаляем. Корректный отказ с причиной учитывается по действующим правилам SLA, но число таких отказов отдельно видно поддержке: хороший процент ответов сам по себе не означает, что пользователь выполнил задачу.

Февральский прогноз — 2 000 проектов, 10 400 шардов, Read 225 000/450 000 RPS и Write 2 450/4 900 RPS в наиболее нагруженной зоне b. Январский максимум был в d; ожидаемые подключения смещают его в b. Пик Read выше 400 000 RPS ожидается не дольше 45 минут. Прогноз 450 000/560 000 = 80,36% устойчивой мощности требует расширения по ПР2 уже в феврале. Планируем добавить две реплики на зону и ресурс YDB, проверить 650 000/7 500 штатно и 600 000/7 000 при одной выведенной реплике. Успешный короткий пик на старой конфигурации не даёт права пропустить эту проверку.

Сначала добавляем ресурс, затем обновляем хосты; подключение новых потребителей намечено на 15.02. Для допуска нужны контрольные чтение и запись, сохранность принятого потребления, отсутствие отставания репорта и пройденный нагрузочный профиль на оставшейся конфигурации. Лид согласует мажор, SRE выпускает канарейку с наблюдением 15 минут. Зоны обновляем последовательно, одновременно выведена не более одной реплики зоны; поломанная реплика тоже расходует этот лимит. Стоп-условия ПР2 проверяются в пятиминутном окне. Отсутствие данных контроля или невыполненная контрольная операция останавливают выпуск.

Для расширения планируем 120 000 ₽/мес., для хранения и чтения истории — 80 000 ₽/мес. поверх наследуемых 260 000 ₽. Это месячные пакеты за все зоны, заказанные с 01.02; развёртывание 12.02 не уменьшает месячную цену. На нагрузочный стенд отдельно отводим 40 000 ₽ разово. Плановый бюджет — 2 160 000 + 460 000 + 40 000 = 2 660 000 ₽ без исходной инфраструктуры, цена которой здесь не задана. Январский временный архив за 12 000 ₽ в феврале повторно не оплачивается.

## Чёрный лебедь

Пятого февраля случается небольшой, понятный команде инцидент. Минорное изменение сокращает таймаут пробы готовности процесса с 200 до 50 мс. Короткие паузы при сборе служебной статистики теперь приводят к исключению исправных процессов из балансировки в зоне b, часть запросов получает ошибку при переключении. Версию откатывают, обращения связывают с I4-PROBE, дежурство возвращается к обычной работе. Это занимает часть предусмотренного сопровождения, но не меняет смысл релиза. Неожиданная проблема обнаруживается через три дня, когда middle 1 передаёт недельное дежурство senior.

Утром 08.02 senior видит спокойную очередь Service desk и собирается вернуться к приёмке истории. Почти одновременно ему пишут три знакомых руководителя проектов: один ждёт обещанную к 12 февраля историю перераспределения лимита, другой — объяснение отличий потребления в двух снимках, третий спрашивает, кому теперь переслать таблицу изменений после смены ответственного. Номеров обращений ни у кого нет. Middle 1 открывает личные переписки и выясняет, что коллеги воспринимали ответы инженера как принятые сервисом обязательства. Они не знали общего канала и продолжали писать тому, кто однажды помог подключить проект.

В переписках есть полезная работа, а не только непрочитанные сообщения: разработчики уже проверяли версии квот, собирали доказательства, обещали выгрузки и ждали согласия владельца другого проекта. Но часть обещаний осталась у конкретного человека, время не попало в L2/L3, а продукт считал этих инженеров свободными для большого экспорта. Восемьдесят четыре сообщения оказываются 52 разными запросами от 12 команд по 18 проектам. Сорок запросов впервые пришли 1–7 февраля, двенадцать тянутся с 27–31 января. Из февральских сорока 24 уже выполнены, а 16 вместе с двенадцатью январскими остаются открытыми: всего 28 незакрытых обязательств.

Теперь выпуск и разбор обещаний конкурируют за одних и тех же людей. Длинный экспорт можно закончить по расписанию, если предложить всем заново обратиться в поддержку и забыть прежние сроки. Для пользователя это будет второе ожидание после уже данного обещания. Можно, наоборот, остановить весь выпуск и вручную выполнить всё, о чём договорились в личных сообщениях. Но среди запросов есть выгрузки чужого проекта без подтверждённых прав и сроки, которые инженер не имел возможности согласовать; кроме того, перенос расширения за 15.02 оставит новый поток на мощности с загрузкой выше порога планирования.

Мы выбираем третий вариант: сохранить основную историю, ограниченный аудитный пакет и расширение, снять большой экспорт и разобрать принятые обязательства с владельцами проектов. Это организационный провал приёма и передачи работы, а не отказ API. Подготовленные ограничения тяжёлых запросов к нему отношения не имеют. Дежурство передаётся внутри прежнего состава, отпуска и уменьшения оплаченных ставок в феврале нет. Меняется представление о том, какая часть этих ставок уже занята.

## Реакция и изменение плана

### Восстановление приёма и проверка данных

08.02 в 09:15 senior фиксирует расхождение между переписками и очередью. Лид как Service owner назначает одного ответственного за каждое обещание; продукт связывается с владельцами проектов, поддержка восстанавливает карточки с исходной датой первого обращения. Ожидание не обнуляем датой регистрации в Service desk. Повторные сообщения связываем по проекту, периоду, операции и предмету запроса, поэтому 84 сообщения не превращаются в 84 обращения или инцидента.

Команда делится по работе. Один специалист поддержки вместе с продуктом выясняет предмет, владельца и ожидаемый результат; senior и middle проверяют версии квот, разрешения и доказательства выполнения. В карточку переносим только рабочие факты и согласованные вложения, с участниками переписки; полные личные архивы не собираем. Отмечаем, кто и когда принял обязательство. Если прежнее обещание выходит за каталог или права заявителя, согласуем допустимую альтернативу, а не выдаём данные по знакомству.

Перед выгрузкой проверяем актуальное согласие владельца, область проекта и получателя. Сопоставляем применённую quota_version, время committed и before/after. Старое сообщение «верните лимит» не разрешает откатить более поздние принятые изменения. Для вопроса о потреблении сравниваем полученную от coremon величину с параметром записи и сохранённым значением QS, учитываем measured_at. Если источник прислал неверное значение, отдаём доказательства владельцу источника; не переписываем потребление или уже принятый репорт, чтобы картинка совпала с обещанной выгрузкой. Для данных до включения истории используем прежние журналы с обозначенной полнотой, а не выдаём их за новую историю.

К 10.02 18:00 все 52 запроса имеют карточку, ответственного, исходную дату и согласованный следующий шаг. Приём и передача работы восстановлены за 2 дня 8 часов 45 минут от обнаружения. Это срок восстановления процесса поддержки, не RTO P1 и не время недоступности API. Двадцать запросов уже нарушили ожидаемый срок ответа или личного обещания: двенадцать январских и восемь февральских. Просрочка остаётся видимой; регистрация не превращает её в своевременное обслуживание.

К 15.02 18:00 из 28 открытых обязательств выполнены 24, по четырём получен мотивированный отказ в запрошенном объёме и подтверждена допустимая альтернатива; исходные заявки закрыты с соответствующим результатом. Вместе с 24 завершёнными до обнаружения получается 48 выполненных запросов и 4 отказа, всего 52. Отказ не записываем как успешную выгрузку. На проверку и обработку известного хвоста ушло 7 дней 8 часов 45 минут; наличие владельцев ещё 10.02 не означало завершения всех пользовательских задач.

Восстанавливаем также учёт уже сделанного труда: 4 ч L2 и 8 ч L3 относятся к 01.02–07.02, подтверждены исполнителями по рабочим записям и помечены как восстановленная оценка. Длительность переписки в часы работы не переводим. После обнаружения затрачены ещё 20 ч L2 и 16 ч L3 на текущий разбор, проверку и выполнение; всего поток личных обязательств добавляет в февральскую отчётность 24 ч L2 и 24 ч L3. SRE тратит ещё 20 ч на сверку сигналов, областей ответственности и полноты разбора как Problem manager. Лид с продуктом снимает из C пакетный экспорт на 62 ч стоимостью 105 250 ₽ внутри фонда. Доступная постраничная история и ограниченный пакет R3 остаются. Критерий закрытия R4-DIRECT — для контрольных запросов сохраняются исходные даты и права, ответственный находит обязательства без прежнего инженера, за семь суток не остаётся необъяснённой разницы между согласованной выборкой рабочих контактов и очередью. Это ограниченная проверка процесса, не обещание знать содержание всех личных сообщений. Выборку собираем с участниками, без постоянного просмотра личных архивов. В дальнейшем регистрация принятой работы и сверка незакрытых обещаний входят в обычную передачу смены; отдельные регулярные часы поверх эксплуатации не вводятся, фактическая ручная обработка учитывается в L2/L3. Наличие общего приёма само по себе ещё не гарантирует выделение часов общих смен под QS.

## Дельта метрик

Сравниваем месячные значения по [правилам учёта](task3.md#метрики). До релиза — опубликованный январский факт; ограничение полноты январского учёта личных обращений описано выше. Для API берём худшее значение среди зон.

| Метрика | Единица | До релиза | Цель | Факт | Δ к цели | Δ к прошлому месяцу |
| --- | --- | --- | --- | --- | --- | --- |
| Доступность Read API | % | 99,95 | ≥ 99,90 | 99,95 | +0,05 п.п. | 0 п.п. |
| p95 Read API | мс | 194 | ≤ 200 | 196 | −4 | +2 |
| Доля неудачных выкаток | % | 5 (1/20) | ≤ 8 | 5 (1/20) | −3 п.п. | 0 п.п. |
| Ручные часы L2 | чел.-ч | 196 | ≤ 160 | 172 | +12 | −24 |
| Ручные часы L3 | чел.-ч | 110 | ≤ 95 | 104 | +9 | −6 |
| Доступность Write API | % | 99,70 | ≥ 99,00 | 99,70 | +0,70 п.п. | 0 п.п. |

Дельта к цели равна факту минус цель, дельта к прошлому месяцу — факту минус январь. Процентные метрики сравниваем в процентных пунктах, остальные — в их единицах. Отрицательная дельта доступности означала бы ухудшение; для p95, доли неудачных выкаток и ручных часов отрицательная дельта означает снижение показателя. Уменьшение ручных часов при изменении полноты учёта само по себе не доказывает рост эффективности.
