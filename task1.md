### Выбранный ИТ-сервис

Сервис квотирования - это наш сервис который отвечает за управления всеми доступными пользователю квотами. Этот сервис хранит эти квоты и предоставляет API другим сервисам, для их изменения + получения текущих лимитов и юзаджа. 

На данный момент квота сервис отвечает за квотирование исключительно метрик.

### Годовой оборот и способ подтверждения

Мы тарифицируем пользователей: 
- по использованию метрик (объем хранения шт, величина потока на запись шт\с)
- по записи логов \ трейсов в секунду (объем ГБ)
- по числу вычисляемых алертов и сработавших эскалаций

### Режим данных

Наши данные - это телеметрия, мы занимаемся ее сбором (свои агенты, фетчеры), приемкой (инжест), обработкой (временные рядя, логи, трейсы) и выстраиванием платформы поверх этих данных (считаем алерты, SLO, рисуем дашики, графики, итд итп). Это если говорить про весь продукт в целом.

Конкретно в QS данные телеметрии мы не храним и не обрабатываем, тут данные - это деревья квот, где по каждому проекту, шарду мы храним узлы с потреблением и лимитами квот.

## Выбранный ИТ-сервис

В качестве сервиса для оценки выбран сервис квотирования

### Зона отвественности

В зону отвественности сервиса квотирования входит:

1. Предоставление Read API для получения текущего значения лимитов и юзаджа квот в проектах и шардах пользователей

2. Предоставление Write API для изменения лимитов в шардах и проектах пользователя

3. Durable хранение данных квот, транзакционность операций редактирования квот

В зону отвественности сервиса квотирования НЕ входит:

1. QS - толлько провайдер данных, сам он никакие квоты не проверяет и не отвечает за корректность проверки. 


### Внешние зависимости

QS достаточно автономные сервис, основные внешние зависимости сводятся к следующим точкам:

1. **YDB** - сервис квотирования сильно завязан на доступность БД, при отсуствии подкючения к БД или при деградации доступа это напрямую скажется на работе сервиса.

2. **Балансер** - на входе в сервис есть балансер, недоступность и ошибки на нем могут привести к ошибки доставки запросов до самого сервиса.

3. CDC топики;

4. Project service - нужен для получения данных о проектах;

### Критерии недоступности \ частичной деградации

Частичную деградацию можно определить как определенный (не высокий) процент запросов на чтение \ запись завершенных с 5хх ошибками.

Полная недоступность - высокий процент ошибок read API, нарушение гарантий записи.

## Выводы по таблицам SLA

Все провайдеры сходятся в том, чтобы считать качество предоставляемых ими услуг на окне в месяц (New relic единственный вводит еще и 2 месячное окно), но все они считают и оценивают это качество по разному, используя разные метрики. AWS и Grapha считают доступность по числу запросов, т.е. по сути оценивают доступность API которое также отображается и на интерфейсе, Axiom считает доступность сервиса в минутах, а New relic в целом не вводит четкого критерия, у них доступность всей системы в целом определяется как возможность войти в систему и увидеть там какие-то данные.

Из-за разных оценок сложно сравнивать предлагаемые уровни доступности, AWS и Axiom предлагают три девятки, графана 99.5, New relic 99.8. Все это достаточно высокие уровни, тем не менее гарантии у всех разные. 

Как мне кажется критерии AWS наиболее строгие так как они оценивают любые запросы в API, дают гарантию в 99.9, а недоступность определяют как любой ответ 500\503.

Помимо уровня доступности интересно также то, как провайдеры оценивают виновника недоступности, что тоже очень сильно влияет на силу гарантий. Например Grapha оставляет за собой право на технические работы раз в квартал, а Axiom вообще не ограничивает число работ, только определяет необходимость уведомления минимум за 7 дней. Такие работы не учитываются при расчёте доступности, это значит что фактически платформа может простаивать намного больше чем описанные 00.1%. Так что очень важно учитывать в SLA возможность плановой недоступности. AWS в свою очередь сужает список таких причин, только до форс мажоров, ошибок пользователя или его ПО, несоблюдение документации, плановой недоступности он не закладывает но, ограждает себя от необходимости отвечать за какие-то непонятные действия пользователей. 

Graphana использует интересный способ ограничивая берстовую нагрузку, фиксируя что если причиной инцидента стал резкий скачок нагрузки, то виноват в этом будет пользователь.

С точки зрения работы с компенсациями все сервисы предлагают примерно одинаковую схему: они дают определенный срок на подачу заявки \ тикета с доказательствами произошедшего инцидента, в качестве доказательст требуется сам инцидент, логи, указание конкретных недоступных функций. У всех провайдеров пользователь теряет возможность заявить об инциденте если с его момента уже прошло определенное время, сроки сервисы дают разные от 2 месяцев у AWS до 10 дней у графаны. New relic поступает немного иначе, они не дают определенных сроков на подачу заявок, а просто фиксируют общую доступность на промежутке и при ее падении ниже определенного уровня дают возможность пользователю в одностороннем порядке разорвать соглашение об использовании их услуг.

В плане компенсаций все провайдеры сходятся в том, что никто не возвращает уже заплаченные деньги, все предлагают кредиты на будущую оплату, ограничиваясь определенным процентом от суммы.

## SLA документ Monium

### Стороны и предмет соглашения

- **Поставщик:** Quota Service, команда Monium.
- **Заказчик:** команды сервисов, использующих Read API и Write API (пуш телеметрии, фетчеры, сервис метабаза - горячее хранилище метрик).
- **Предмет:** предоставление API и хранение лимитов и потребления квот метрик для проектов и шардов Monium.
- **Область действия:** разделена на зоны доступности (показатели рассчитываются отдельно для каждой)
    - ru-central1-a;
    - ru-central1-b;
    - ru-central1-d;
    - ru-central1-e.

### Сущность услуги

В услугу входят:

- Read API для получения текущих лимитов и потребления квот.
- Write API для изменения лимитов проектов и шардов; перечень операций: установка квоты храним метрик, установка квоты записи метрик, перемещение квоты между проектами.
- Долговременное хранение данных квот и транзакционность изменений в пределах шардах (конкурентные изменения корректно линеаризуются в рамках шарда).

В услугу не входят проверка соблюдения квот другими сервисами, ограничение потоков телеметрии, хранение самой телеметрии и биллинг. За применение полученных лимитов отвечает читатель.

Зависимости: YDB, входной балансер, CDC-топики и Project сервис. Отказ зависимости, повлиявший на QS, учитывается в SLA.

### Цели соглашения

- **Доступность Read/Write API:** потребители могут получать и изменять квоты; измеряется долей успешных запросов чтения и записи.
- **Скорость ответа:** QS не создаёт неприемлемую задержку для потребителей; измеряется p95/p99 времени ответа.
- **Целостность и актуальность:** изменения лимитов не теряются и становятся видны потребителям; измеряются нарушениями гарантий записи и задержкой видимости изменений.
- **Ёмкость:** QS выдерживает согласованную нагрузку; измеряется RPS чтения/записи и объёмом данных квот.
- **Восстановление:** влияние инцидентов ограничено по времени; измеряется временем реакции и восстановления, RTO/RPO.

### Целевые уровни обслуживания

**Доступность**

- Read API: доступность ≥ 99.95%; Write API: ≥ 99%.
- Формула для каждого API: `100% × (учитываемые запросы − неуспешные запросы) / учитываемые запросы`.
- Неуспешный запрос для Write API: ошибка сервиса, невозможность соединения или превышение таймаута 5s. Коды ответа: 5xx
- Неуспешный запрос для Read API: ошибка сервиса, невозможность соединения или превышение таймаута 500ms. Коды ответа: 5xx
- Режим работы: круглосуточно. Отчётный период месяц.
- Плановые работы: отсутствуют, релизы катаются непрерывно. 

**Производительность**

- Успешные Read-запросы: p95 ≤ 200ms, p99 ≤ 500ms; Write-запросы: p95 ≤ 1s, p99 ≤ 5s. Окно расчёта: месяц.
- Успешные (2xx,3xx,4xx) Read-запросы: 99.95%, Write-запросы: 99%. Окно расчёта: месяц.

Высокая производительность API чтения квот обусловлена критичностью сервиса для работы всего Monium, нарушения в чтении квот могут привести к недоступности записи телеметрии.

В свою очереь производительность Write API снижена за счёт сильно более низкого уровня критичности в бизнес процессах.

**Ёмкость**

- Чтение 400к RPS, запись 5к RPS; допустимый пик чтения 600к RPS длительностью 1 час.

Рассчитана на основе данных по числу клиентов и объему записываемой телеметрии, для рассчёта использовалось значение записи в 3млрд. метрик/секунду.

**Поддержка**

- P1: массовая недоступность Read API или нарушение гарантий записи: реакция <=10 минут, восстановление 1 час, обслуживание 24x7.
- P2: частичная деградация чтения/записи: реакция 10 минут, восстановление 2 часа, часы обслуживания 24x7.
- P3: незначительные сбои системы или некритичных бизнес-процессов: реакция 1 час, решение 6 часов, часы обслуживания - рабочие часы без выходных.
- Р4: небольшие проблемы или запросы, существенно не влияющие на работу бизнеса: реакция 1 час, решение 24 часа, часы обслуживания - рабочие часы без выходных.

### Роли и отвественности

**Поставщик** обеспечивает:
- работу API 
- хранения данных
- мониторинг
- дежурство
- восстановление и разбор инцидентов. 
- уведомление заказчика о возникновении инцидента, 
- актуализацию статуса сервиса

**Заказчик** должен:
- соблюдать контракт API  
- в рамках работы над инцидентом предоставлять поставщику необходимые технические данные и контакт
- пре уведомлении поставщика о возникновении ошибок, предоставлять подтверждения в виде: идентификаторы запроса \ логов. 
- реализовать обработку ошибок согласно контракту API

### Мониторинг и отчетность

- Метрики измеряются платформой Monium, для обеспечения доступности и корректности измерений все инсталляции мониторятся в 2 экземплярах - сами у себя и у соседней инсталляции;
- Периодичность рассчёта алертов (окно) на доступность системы - 5 минут;
- Журналы инцидентов ведет инфраструктурная платформа Yandex Cloud.

Инцидент заводится по факту фиксации деградации \ недоступности, флоу обработки инцидента:

1. Старт инцидента - регистрация инцидента
2. Работа над восстановлением сервиса - фиксация ETA, периодическая фиксация статусов (раз в 10 минут)
3. При возникновении трудностей, дополнительных проблем ETA обновляется с уведомлением пользователя
4. Сервис восстановлен - пользователи уведомляются о восстановлении сервиса

### Ответственность за невыполнение

Отвественность за невыполнение несет сервис Monium metrics 

Размер компенсации в зависимости от доступности API чтения квот `X` 

- `X ≥ целевого уровня`: кредит 0%.
- `99.5% ≤ A < целевого уровня`: кредит 10%.
- `99% ≤ A < [порог B]`: кредит 20%.
- `A < 98%`: кредит 30%.

### Процедура эскалации

1. **Дежурный Monium:** принимает сигнал или обращение, подтверждает инцидент и начинает диагностику в срок своего приоритета.
2. **Технический руководитель:** подключается, если нет реакции дежурного в течении описанного по приоритету времени или нужна помощь владельца зависимости. 
3. **Владелец сервиса и представитель заказчика:** подключаются при риске нарушения RTO, потери данных или длительном влиянии на потребителей. 

Обновления статуса: каждые 10 минут для P1 и P2. Разбор причин и план действий предоставляются в течение недели после восстановления.

### Пересмотр и действие соглашения

- Регулярный пересмотр: раз в месяц; инициатор Monium.
- Внеочередной пересмотр: рост нагрузки выше 120% от предыдущей целевой, крупный инцидент, изменение архитектуры/зависимостей, добавление инсталляции или новых видов квот.
- Изменения согласуются за 2 недели до вступления в силу. Новые правила не меняют расчёт завершённых периодов.

### Глоссарий

- **QS:** сервис хранения и предоставления данных о квотах метрик; проверку соблюдения квот выполняют потребители его API.
- **Лимит / потребление:** установленное ограничение / учтённое использование ресурса.
- **Доступность:** доля успешных учитываемых запросов Read или Write API за согласованный период, с учётом исключений.
- **Инцидент:** событие, нарушающее или угрожающее согласованному уровню услуги; приоритет определяется масштабом и последствиями.
- **Время реакции:** от согласованного начала отсчёта до подтверждения специалистом принятия инцидента в работу.
- **Время восстановления / решения:** до восстановления согласованной функции / до выполнения условий закрытия инцидента. Обходное решение и окончательное исправление фиксируются отдельно.
- **Рабочее время:** 08:00 - 18:00 по часовому поясу клиента, без выходных и праздников. Режим 24×7 включает выходные и праздники.
- **p95 / p99:** время, за которое завершаются соответственно 95% / 99% измеряемых запросов.
- **RTO / RPO:** допустимое время восстановления / допустимое окно потери данных по времени.
- **Сервисный кредит:** согласованное уменьшение будущей платы или внутренних начислений при нарушении SLA.
